# AquaSense — Machine Learning Model

> Predictive Water Freshness Forecasting
> This document explains the model architecture, training process, and integration plan.

---

## Purpose

AquaSense predicts how long water in a tank will remain within acceptable quality parameters before degradation sets in. The system outputs two values for every tank, never a binary safe or unsafe verdict.

| Output                   | Range          | Meaning                                             |
| ------------------------ | -------------- | --------------------------------------------------- |
| `freshness_window_hours` | 2 to 24+ hours | Estimated time before water quality degrades        |
| `risk_score`             | 0.0 to 1.0     | Overall risk level based on current sensor readings |

---

## Model Type

Two separate Random Forest Regression models, trained using scikit-learn.

**Why Random Forest:**

- Handles non-linear relationships between sensor values well
- Robust to outliers and noisy sensor data
- Does not require feature scaling
- Interpretable through feature importance analysis
- Well suited for tabular sensor data with a moderate number of features

**Why two separate models instead of one:**
`freshness_window_hours` and `risk_score` are related but distinct outputs. Training separate models for each allows each model to specialise on its specific target rather than compromising on a combined loss function.

## Training Data

**Source:** Synthetic sensor readings generated by `backend/scripts/generateData.js`

**Size:** 500 readings

**Distribution:**

- 60% normal water conditions
- 20% warning level conditions
- 20% poor water quality conditions

**Why synthetic data:** Real hardware sensor data was not yet available during the model development phase since the ESP32 firmware had not been deployed. Synthetic data was generated using domain knowledge of WHO water quality thresholds to create a realistic relationship between sensor values and water freshness degradation.

**Important limitation for defense:** Training labels (`freshness_window_hours` and `risk_score`) were calculated using a deterministic formula based on sensor values, not measured from real water degradation over time. This means the model's high accuracy reflects how well it learned the formula, not real world water chemistry. Once real hardware data is collected over time, the model should be retrained on actual measured outcomes for production use.

## Model Performance

| Model            | R² Score | Mean Absolute Error |
| ---------------- | -------- | ------------------- |
| Freshness Window | 0.9968   | 0.23 hours          |
| Risk Score       | 0.9959   | 0.0052              |

**Hyperparameters used:**

```python
RandomForestRegressor(n_estimators=100, max_depth=10, random_state=42)
```

## Training Process

1. Exported 502 historical readings from Firestore to CSV using `backend/scripts/exportToCSV.js`
2. Loaded CSV into Google Colab using pandas
3. Split data 80/20 into training and testing sets
4. Trained two `RandomForestRegressor` models, one per target output
5. Evaluated using R² score and mean absolute error
6. Exported both models as `.pkl` files using joblib

**Notebook location:** `ml-model/notebooks/AquaSense_Model_Training.ipynb`

## Integration Plan

The forecast endpoint currently returns mock data from `backend/src/controllers/forecastController.js`. The integration plan is:

1. Set up a Python microservice or use a child process to run the `.pkl` models from Node.js
2. Replace the mock response in `getForecast` with real model predictions
3. Pass the tank's current sensor values as input features
4. Return the predicted `freshness_window_hours` and `risk_score`
5. Optionally cache predictions for a short period to reduce computation on every request

**Why not load the pkl directly in Node.js:** scikit-learn models are Python objects and cannot be loaded directly in JavaScript. The two standard approaches are running a small Python script as a child process from Node, or running a lightweight Python Flask or FastAPI microservice that the Node backend calls internally.

---

## Retraining Strategy

As the ESP32 firmware collects real sensor data over weeks and months, the model should be periodically retrained on real readings instead of synthetic data. This would require:

1. Manual or automated water testing to establish ground truth freshness windows
2. Exporting accumulated real readings from Firestore
3. Retraining using the same notebook structure with real data
4. Comparing performance against the synthetic baseline established here
